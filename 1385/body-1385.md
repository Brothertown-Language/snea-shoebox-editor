## Problem

The records page has no way to use the semantic gloss search the db/embed specs deliver: the mode radio exposes only Headword/Gloss/Lexeme/FTS, there is no similarity-threshold control, no similarity-score display, and no handling for semantic-search degraded-state payloads. Linguists need the end-user surface of semantic search on the app's primary search page.

## Scope

- Two new mode radio entries (Semantic Gloss, Semantic All) added to the existing records-page radio, adding caption dict entries while preserving the single selected-mode caption pattern; language selectbox and language-role radio disabled with explanatory help text in semantic modes (mirroring the FTS disabled-filter idiom — the seam accepts only `source_id`, so the source filter stays live).
- A per-user similarity-threshold preference control — slider + numeric input, two-way coupled, proportion in [0.0, 1.0] displayed as decimal (default 0.80), invalid edit rejected with snap-back — rendered in a stable sidebar slot (below the mode caption, above the search/clear buttons) present in ALL modes with the widgets disabled and help text in non-semantic modes; persisted via PreferenceService (`records`/`semantic_threshold`, default `0.80`).
- Similarity scores on semantic-mode result rows in descending order, rendered inline in each record card's header line (not behind a disclosure/expander) as fixed two-decimal theme-aware values; exact-match modes render unchanged.
- Rank-once pagination: page navigation slices the service's full ranked list; no re-rank or re-invocation on page change.
- Clean empty-state rendering in the MAIN panel for every seam status (`empty_query`, `no_embeddings`, `stale_model`, zero-below-threshold) — st.info for informational states, st.warning for remedy-required states, with stale/no-embeddings messages naming the admin backfill remedy.

**Out of scope (owned by the db/embed spec #36):** embedding model artifacts, pgvector schema/migrations, search service internals, admin backfill button, calibration, DDL. Threshold storage layer (`preference_service.py`) is consumed as-is in both specs.

## Approach

Bind the records page to the `search_semantic` seam contract (v1 field list: `results: list[(record_id, score)]`, `status` enum, `message`) — the UI layer imports nothing below the service seam. Mode selection dispatches through the existing `search_records` entry with the additively-widened SearchMode values, so existing modes' behavior is regression-safe. The threshold control follows the developer-decided widget contract (stable slot in all modes, disable-with-reason outside semantic modes — consistent layout beats reflow-on-mode-flip) and persists per user via the existing PreferenceService. Pagination follows rank-once slice semantics: the service returns the full ranked list once, page navigation only slices it, so ordering can never change mid-paging. Result rendering gains one semantic branch for inline score display and status-keyed, main-panel empty states built from theme-aware native Streamlit elements (no hardcoded colors, no new iframe CSS).

## Impact

- **Risk: regression on the highest-traffic page** — SC-7's behavioral harness guards the four existing modes' results; mode keys, session-state keys, and filter behavior in existing modes preserved (`records.py` verified; SC-8 guards the FTS disabled-filter idiom).
- **Risk: seam mismatch during cross-spec development** — UI binds only to the v1 contract enumerated in the analysis artifacts; any status-enum extension is a versioned contract migration. Key dependency: #36 delivers the seam first.
- **Risk: preference corruption via invalid widget input** — snap-back validation (SC-3) plus persistence round-trip verification (SC-2) on real synced data.

Call to action: review; this spec implements after #36's db/embed items 5 (seam) land.
